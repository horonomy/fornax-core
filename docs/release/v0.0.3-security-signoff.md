## Findings

### SEC-v0.0.3-0001 (High, fixed) — `ExtensionEnvelope` bypassed redaction

FORNX-158's `Evidence.extension` is a second path into storage/export
alongside `Evidence.payload` — the exact shape of data flow FORNX-280
(the v0.0.1 Critical) already found and fixed for `tool_input`/
`Claim.text`. `fornax-daemon`'s `handle_message` redacted `payload` but
never touched `extension.fields`/`extension.unknown` before this fix.

opencode's `tool.execute.after` sensor is the first real
`ExtensionEnvelope` producer (`crates/fornax-adapter-opencode/src/lib.rs`'s
`build_tool_telemetry_extension`) and carries the bash tool's own command
string in `title` — demonstrably as attacker/agent-controlled as
`tool_input`, e.g. `curl --api-key <secret> https://...`. `fornax
export-spool` spools `Evidence` "as-is" including `extension`
(`evidence_envelope_carries_extension_data_through_export`,
`crates/fornax-cli/src/main.rs`), the same egress path FORNX-280 closed for
`payload`.

**Fix** (this PR): apply `redact_json` to both `extension.fields` and
`extension.unknown` at the same daemon ingestion boundary as `payload`.

**Non-vacuity proof**: added
`extension_fields_and_unknown_are_redacted_before_storage`
(`crates/fornax-daemon/src/main.rs`), following the FORNX-280 canary
pattern. Reverted the new redaction lines and re-ran: the test failed with
the raw canary marker present in the stored `extension.fields` and
`extension.unknown`. Restored the fix and re-ran: passed.

No pre-fix stored rows carry extension data needing a backfill — opencode
is the only `ExtensionEnvelope` producer in the codebase and this is its
first release.

### SEC-v0.0.3-0002 (High, fixed) — cross-provider capability-cache downgrade

`fornax-daemon`'s in-memory `state.caps` (a
`HashMap<session_id, RuntimeCapabilities>`) is the slot `handle_message`'s
`Claim` arm reads to gate every verifier's `is_observable` check. It had no
provider discriminator, but `session_id` is provider-controlled data — an
adapter reads it straight off its own native payload (e.g. opencode's
`/input/sessionID`, `crates/fornax-adapter-opencode/src/lib.rs`). A
`Capabilities` announcement naming an already-active session id from a
*different* provider than the one already cached silently overwrote that
session's snapshot — a real capability **downgrade** that could suppress
verification and hide evidence, verbatim FORNX-244's "capability
spoofing/downgrade" Security Focus bullet.

The persisted store was never at risk: `Store::upsert_capabilities` is
correctly scoped to `(session_id, provider)` (one row per announcing
provider, `crates/fornax-store/src/lib.rs`) — only this in-memory read path
collapsed multiple providers into one slot.

This is a pre-existing daemon design gap (the single-slot cache predates
opencode), but v0.0.3 is exactly what makes it concretely reachable: it is
the first release where three providers can announce capabilities against
the same running daemon, and the review this ticket calls for is exactly
what should catch this before that becomes a live multi-provider
deployment shape.

**Fix** (this PR): a same-session announcement from a provider different
than the one already cached is dropped from the in-memory cache (logged as
a warning) rather than overwriting it; the correctly-scoped store row is
still written either way.

**Non-vacuity proof**: added
`cross_provider_capabilities_announcement_does_not_clobber_cached_session`
(`crates/fornax-daemon/src/main.rs`). Reverted the provider-match guard
(back to the pre-fix unconditional `cache.insert(sid, caps)`) and re-ran:
the test failed — a spoofed `OpenCode` announcement downgraded the cached
`ClaudeCode` session's `FinalResponse` capability from `Available` to
`Unavailable`. Restored the fix and re-ran: passed.

**Scope note**: this fix closes the concrete spoofing/downgrade exploit
path (a forged `session_id` clobbering another provider's cached
capabilities). It does not implement full multi-provider-per-session
capability semantics — the daemon's `Claim`/verifier pipeline still reads a
single `RuntimeCapabilities` value per session, consistent with every
current adapter and fixture's one-provider-per-session assumption. A
legitimate future multi-provider-per-session design (if one is ever
needed) is out of this fix's scope and would need its own design pass, not
a security patch.

### SEC-v0.0.3-0003 (Informational, accepted risk) — `fornax-hook-opencode` resolved via bare `PATH` lookup

`plugin/fornax-capture.js` spawns `fornax-hook-opencode` by bare name,
`PATH`-resolved, from inside opencode's own process. Same trust class as
the already-accepted `SEC-v0.0.1-0005` (no privilege boundary crossed — the
spawned binary runs as the invoking user, and `PATH` is under that same
user's control). A missing/wrong-`PATH` binary silently drops opencode
evidence collection with no user-visible signal (`stdio: ["pipe", "ignore",
"ignore"]`) — a silent availability gap, not a confidentiality/integrity
one. Accepted as residual risk; not currently blocking.

### SEC-v0.0.3-0004 (Informational, fixed) — FORNX-161's two disclosed opencode failure modes are confirmed fixed

FORNX-161's Jira comment disclosed two concrete opencode adapter failure
modes. Both were reviewed directly against `plugin/fornax-capture.js` and
confirmed already fixed in the code this candidate ships:

1. **"Silent EPIPE if `fornax-hook-opencode` isn't on `PATH`"** — in fact
   worse than a silent EPIPE: an unhandled `error` event on the spawned
   `ChildProcess` is a fatal, uncaught exception in the *parent* process —
   and the parent here is opencode itself, since this plugin runs
   in-process. `child.on("error", ...)` and `child.stdin.on("error", ...)`
   listeners (lines 31–39) now swallow it, matching the file's own
   documented best-effort intent: a best-effort integration must never take
   down its host on a missing/dead binary.
2. **"`dispose()` not waiting for queued writes to flush"** — `dispose()`
   now awaits `child.stdin.end()`'s callback (lines 56–70), bounded by a
   200ms timeout so a dead/hung child can never delay opencode's own
   shutdown, closing the race that could previously drop the last queued
   event on a fast opencode shutdown.

Both fixes are present in the exact code reviewed for this candidate
(`cc7ed3f`). `crates/fornax-adapter-opencode/tests/live_transport.rs` is
the automated CI regression for the transport leg these fixes protect
(real plugin file, real `fornax-hook-opencode` process, real
`fornax-daemon`, real Unix domain socket).

**Disposition: no Jira Bug needed.** Both are data-loss/reliability nits,
already fixed, not open gaps — recorded here per this ticket's explicit ask
to assess whether either "needs a Jira Bug filed or is acceptable as
documented residual risk." Neither applies; both are closed.

## Checklist against FORNX-244's Security Focus bullets

| Bullet | Result |
|---|---|
| Capability spoofing/downgrade | **Real defect found and fixed**: SEC-v0.0.3-0002. `RuntimeCapabilities` *values* are never derived from provider payload data (`probe()` is a fixed per-adapter-version declaration) — that half of the concern is clean. The `session_id` used to key the announcement is provider-controlled, and the daemon's in-memory cache didn't discriminate by provider — that half was not. |
| Malformed/oversized payloads, extension-field injection, parser/resource exhaustion | Adversarial coverage already exists and holds for opencode: malformed/missing/unknown-shape hooks return `Unrecognized`/`Ignored`, never panic (`crates/fornax-adapter-opencode/src/lib.rs` tests); an incompatible `ExtensionEnvelope.schema_version` is rejected explicitly (`crates/fornax-adapter-conformance/tests/contract.rs`). No adapter-specific size cap exists on the daemon's UDS line reader (`BufReader::lines()`), but this is pre-existing across all three adapters (exercised up to 5MB strings without a crash by `crates/fornax-daemon/tests/adversarial_daemon_input.rs`), not introduced by opencode, and the socket is local/same-user only (`daemon_socket` boundary) — not re-opened as a new finding here. |
| New signal fields cannot bypass redaction/classification/egress policy | **Real defect found and fixed**: SEC-v0.0.3-0001. |
| Provenance/trust-class is not forgeable merely by provider payload data | Confirmed clean. `CollectionMethod`/`Evidence.provenance` are hardcoded per sensor at construction time (e.g. `OpenCodeExitCodeSensor::collection_method` always returns `HookCallback`; `provenance` is built via `format!(...)` with no untrusted interpolation of the trust-relevant part) — reviewed directly in `crates/fornax-adapter-opencode/src/lib.rs`. |
| Third-party/provider-specific content treated as untrusted (browser/log/serialization injection) | No new sink found. Daemon logging (`tracing::*` calls in `crates/fornax-daemon/src/main.rs`) never logs raw/unredacted `tool_input`/`raw`/`extension` content; the one log line that includes claim text (`claim = %claim.text`) logs it *after* `redact_text`. `browser_rendering_injection` (the `fornax-cloud` dashboard) is out of this repo's touched surface for this candidate — no new rendering path was added here. |
| Dependency/provider API update review | No new Cargo dependency in `fornax-adapter-opencode` (`serde`/`serde_json`/`tokio`/`anyhow`/`chrono`/`uuid`, all pre-existing workspace-pinned versions). No new npm dependency in `plugin/fornax-capture.js` (`node:child_process` only, a Node builtin; no `package.json` for this plugin at all). |
