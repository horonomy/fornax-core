## DR/restore in detail (AC3) — the one judgment call in this sign-off

**What was actually measured**: FORNX-214's drill seeded synthetic failure
data, destroyed it, and recovered via Neon snapshot/restore — RPO ~76s,
RTO ~27s, both well inside the <5-minute target, with verified FK
consistency and safe double-replay idempotency. Real, solid evidence — but
against the Neon project's **root branch**, not `production`/`beta`.

**What FORNX-439 re-confirmed live (2026-10-09)**: Neon's snapshot/restore
mechanism only operates on a project's root branch; `production` and `beta`
are non-root children. No time-travel branch-creation escape hatch exists on
the current Neon API surface (`create_branch` takes no LSN/timestamp
parameter). Even root-snapshotting doesn't substitute, because it only
recovers the shared fork-point ancestry, not `production`/`beta`'s own
3+ weeks of independent post-fork history. The only real mitigation — a
scheduled `pg_dump` outside Neon's branch mechanism — **has not been
built**. FORNX-439's own recommendation: *"Declare the current, true DR
posture for v0.0.9 rather than assume coverage that doesn't exist."*

**Why this AC is CONDITIONAL-PASS, not a clean PASS or a flat NO-GO**: the
AC's own wording offers two ways to pass — "meets... declared targets" (it
doesn't, for `production`/`beta`) **or** "truthfully revises" them (it
does — FORNX-225's merged docs state the gap plainly, matching FORNX-439's
own recommendation word for word). The *documentation* obligation this AC
creates is satisfied. The *operational capability* the documentation is
honestly disclosing the absence of is **not** satisfied, and that is the
part that actually matters for a production incident. Marking this a clean
PASS would be exactly the "manufactured green verdict" this campaign's
standing instruction prohibits; marking it a flat NO-GO would ignore that
the disclosure obligation genuinely was met. CONDITIONAL-PASS is the honest
middle: the paperwork is done, the capability is not.

A related hardening gap noticed in passing (not fixed, not blocking):
`production`'s Neon branch has `protected: false` (Neon's free-tier plan
allows zero protected branches) — flagged for a future hardening ticket.

## Security Focus (additional checks beyond the 6 ACs)

- **Resource-exhaustion/DoS, oversized/poison events, retry amplification,
  noisy-neighbor**: covered — FORNX-212's local-daemon `ingest_quarantine`
  (durable, not silently dropped; 512-concurrent-event test proves zero
  loss within a bounded drain time against the daemon's 256-connection
  cap) and cloud-side Pub/Sub native DLQ wiring (code-only, see below);
  FORNX-432's deterministic 100,000-work-unit budget bounds the
  evidence-independence construction cost specifically.
- **Degraded-mode auth/redaction/policy must not fail open under
  load/outage**: PASS — every budget-exceeded/degraded path in FORNX-432
  fails to `Review`/`Unknown`/`Unverified`/outright-refusal, never a
  partial result and never a silent `Verified`. This is the literal
  "fail-safe, not fail-open" property the AC asks for, proven by real
  tests, not just argued.
- **Production IAM/secrets/observability/logging/backup-access review**:
  **thin, stated honestly rather than inflated**. This release cycle did
  not perform a fresh IAM/secrets audit; the only evidence is FORNX-48
  (isolation, prior release, still Done and unrevised) and FORNX-153's
  existing minimal alerting (Cloud Run/Pub/Sub built-in metrics + one
  log-based DB-connectivity metric, also pre-existing). No new backup-access
  or logging-leakage review was performed this cycle. Not a finding against
  v0.0.9 specifically — just not fresh evidence, and this sign-off will not
  claim otherwise.
- **DR/restore cannot bypass tenant isolation, key policy, or retention
  semantics**: **N/A — untestable**, honestly. Since no restore mechanism
  exists for `production`/`beta` at all (see AC3), there is nothing to test
  a bypass against. This is not a passing result; it is the absence of a
  mechanism to evaluate.
- **Public SLO/scale/HA claims must match measured evidence**: PASS, same
  evidence as AC6 — independently re-read, no overclaim found.
- **Evidence admission must be enforced on every verdict-bearing surface,
  not asserted from one choke point**: **NO-GO (FORNX-441)**. A live
  reproduction against the real `/api/contract` endpoint confirmed a
  registered-but-unauthorized sensor forging a `HostObserved` label (the
  fornx380-11 attack shape) reached contract satisfaction before the PR
  #246 fix — this was not a theoretical code-reading finding, it was
  demonstrated. `/api/fusion`/`/api/decision`/`/api/judge`/`/api/reverify`/
  receipt issuance have not yet been confirmed exploitable the same way
  (not yet attempted) or fixed; both are required before this item can
  move off NO-GO. Exploitability/impact/reachability for the remaining
  surfaces must be established with the same rigor — reproduced, not
  assumed — before any final severity label (High vs. Critical) is
  claimed.

## What this sign-off does not do

It does not block FORNX-263 (release execution) outright — that decision
belongs to whoever owns the final go/no-go call, per this campaign's
standing instruction to report NO-GO honestly rather than decide unilaterally

is not, and the reason it is not is a real, disclosed, unresolved production
DR capability gap — not a paperwork gap this document could close by itself.
