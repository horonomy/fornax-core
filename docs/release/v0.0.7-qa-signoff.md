## What this covers

All 13 real FORNX-70 children (FORNX-314–326) genuinely Done (a separate
stale-duplicate set, FORNX-125–133, was marked superseded earlier this
session and is not part of this scope):

- **Tamper-evident local audit ledger** — hash-chained entries, three
  independent divergence checks (missing-sequence, relinked-prev-hash,
  hash-mismatch), plus truncated-tail detection via a persisted high-water
  mark.

  session).

  tampered chain shows up in the report, it isn't hidden.
- **Bounded, resumable retention sweeps** — each call processes one bounded
  batch (test-asserted), never the whole backlog in one pass.

## Fresh, independent security/QA review (this release, 2026-09-24)

A separate pass reviewed:

1. **SQL injection re-verification** — 5 `sqlx::AssertSqlSafe` call sites
   (required by the sqlx 0.9 upgrade's stricter `SqlSafeStr` trait)
   individually re-checked, not just trusted from the isolation pass —
   confirmed each interpolates only a compile-time-constant identifier
   array (`RECEIPT_COLUMNS`, `KNOWN_RECORD_TABLES`), never runtime or
   request-derived input. No findings.
2. **Audit-log tamper-evidence** — `verify_audit_chain_conn` genuinely
   recomputes and compares hashes; not computed-and-ignored. Tested:
   `direct_sql_delete_of_trailing_rows_is_detected_as_truncated_tail`,
   `truncated_tail_survives_a_subsequent_legitimate_append`. No findings.
3. **Retention/deletion correctness** — bounded sweep batches confirmed;
   fornax-core's retention module has no `legal_hold` concept by design
   (a purely local-device data-lifecycle boundary, distinct from
   fornax-cloud's separate tenant-level legal-hold control) — a legitimate
   architectural boundary, not a gap. No findings.
4. **Compliance report accuracy** — surfaces real verification results, no
   omission path found. No findings.
5. **Checkpoint submission resource bounds** — `MAX_RESPONSE_BYTES` (64KB)
   enforced. No findings.
