# Fornax v0.0.9 — Operational Scale & Reliability

**Status:** Not yet tagged/executed as a release (FORNX-263 release
execution has not run as of this writing). This document records the real,
independently-verified engineering state of the v0.0.9 candidate so the
release-execution/QA gates (FORNX-262/263/264) have an honest baseline to
work from — it is not itself a release announcement. The Jira Fix Version
`Fornax v0.0.9 — Operational Scale & Reliability` also does not yet exist
as a native Jira object (FORNX-430, owner-blocked — see "Known
limitations").

## What this is

Fornax v0.0.9 (Stage 7A, epic FORNX-146, HVDL-15) is a production-hardening
release: it proves (or honestly fails to prove) that Fornax continues to
accept, preserve, explain, and recover critical evidence under
representative load and failure conditions — not new product surface.

- **Evidence-ingress provenance and replay enforcement** (FORNX-431) — the
  daemon's real verdict-persistence choke point (`run_verifiers_and_persist_findings`,
  the one call all three live verdict paths route through) now filters
  evidence through a provenance guard before any verifier sees it, and
  checks a durable consumption ledger before persisting a `Verified`
  finding. A forged trust-class label, an unregistered sensor, a session
  claiming the wrong owning provider, and a claim reusing evidence already
  consumed by an unrelated claim are all quarantined or downgraded to
  `Review`, never silently verified. Independently re-verified against the
  live daemon under real concurrency (FORNX-435): forged sensor trust,
  foreign-session/provider mismatch, sequential and *concurrent*
  cross-claim replay, a legitimate positive control, and same-claim retry
  idempotency all hold. See `docs/adr/0024-evidence-ingress-provenance-and-consumption.md`.
- **Evidence-independence capacity bounding** (FORNX-432) — the
  evidence-family construction pass disclosed in v0.0.8 as an
  `O(n² log n)` scalability limitation is now benchmarked on frozen
  synthetic adversarial fixtures, sped up 10–143x on common shapes with
  byte-identical output (proptest-proven against a frozen reference
  oracle), and bounded by a deterministic 100,000-work-unit budget that
  aborts construction rather than completing on a poisoned pool — fusion
  fails safe to `Review`, contract satisfaction to `Unknown`, receipt
  issuance refuses outright, and the daemon runs the bounded cost via
  `spawn_blocking` so one poisoned session cannot stall a concurrent clean
  one. Independently re-verified (FORNX-436), including a fixture-potency
  negative control proving the guard is structurally load-bearing, not
  dead code. See `docs/research/fornx-432-independence-capacity.md`.
- **Local-daemon critical-evidence quarantine and backpressure**
  (FORNX-212, local-daemon scope) — a malformed or unprocessable ingest
  line is now durably recorded (`ingest_quarantine` table, with retention
  sweep coverage), not just logged and dropped; a real 512-concurrent-event
  load test proves zero loss and bounded drain time against the daemon's
  256-connection inflight cap.
- **Cloud-path capacity measurement** (FORNX-211, cloud-path scope) — a
  real bounded load run against Beta's live stack: 300/300 ingest
  requests succeeded (100%, vs. 99.5% target), `/readyz` 100% (20/20, vs.
  99.5% target), SaaS availability 100% (20/20, vs. 99% target). One
  measured gap, not silently dropped: Pub/Sub message-age (the processing
  leg's other SLI) could not be measured — no Cloud Monitoring access into
  the Beta GCP project existed for this campaign. See `fornax-cloud`'s
  `docs/fornx-211-cloud-path-results.md`.
- **Cloud-side DLQ and non-critical-telemetry sampling** (FORNX-212,
  cloud-path scope) — Pub/Sub's native dead-letter-topic mechanism is now
  wired (Terraform, both Beta and Production) for the ingest-events
  subscription, and an explicit, deterministic, measurable sampling policy
  exists for the one genuinely non-critical message type
  (`CapabilitiesMessage`), defaulting to 1.0 (keep everything) since no
  real backlog-pressure signal exists yet to justify dropping anything.
  **The DLQ Terraform is merged but not applied to live Beta/Production
  infrastructure** — this campaign's GCP credentials have no project
  access to apply it; that is an explicit owner decision, not taken here.
  See `fornax-cloud`'s `docs/fornx-212-cloud-dlq-backpressure.md`.
- **Storage growth and stay-on-Postgres decision** (FORNX-213) — real
  measured growth (~2.1 KB per session bundle, linear through 100,000
  synthetic sessions) and flat, index-backed read-path latency through the
  same range. Decision: stay on Postgres/Neon — nothing measured justifies
  Kafka, ClickHouse, BigQuery, or a split analytical store. See
  `fornax-cloud`'s `docs/fornx-213-storage-benchmark.md`.
- **Database disaster-recovery drill** (FORNX-214) — a real seeded-failure
  drill (synthetic data destroyed, then recovered via Neon snapshot/restore)
  measured RPO ~76 seconds and RTO ~27 seconds, both well inside the <5
  minute targets, with verified FK consistency and safe double-replay
  idempotency. **This drill ran against the Neon project's root branch, not
  against `production`/`beta` directly** — see "What this release does not
  claim" below; this is the single most important caveat in this entire
  document.

## What this release does not claim

- **Production/Beta database point-in-time restore is NOT proven and does
  not currently work.** FORNX-214's drill measured real RPO/RTO numbers,
  but Neon's snapshot/restore mechanism only operates on a project's root
  branch; `production` and `beta` are non-root child branches and cannot be
  directly snapshotted — confirmed live, twice, independently (FORNX-214's
  original finding, re-confirmed current by FORNX-439's follow-up
  investigation). The real mitigation identified (a scheduled `pg_dump`
  outside Neon's branch mechanism) **has been built, merged, and verified
  against a real published container image on a disposable non-production
  Neon branch — but has not been activated in production.** Activation
  needs three owner-only actions (generate the `age` recovery key, store it
  per the documented custody procedure, and run the first `terraform
  apply`) and, after that, a real production restore drill — none of which
  this campaign's credentials/authorization can perform. **Do not read the
  ~76s/~27s RPO/RTO numbers above as a production guarantee — they describe
  the restore mechanism's speed on disposable data, not a demonstrated
  production recovery, and still won't until the real drill runs.**
  FORNX-439 remains open, tracking activation and the drill as a real,
  disclosed release-boundary question rather than a resolved item.
- **Pub/Sub message-age (the processing leg's SLI) is unmeasured.** No
  negative result exists either way — this campaign simply never had Cloud
  Monitoring access into the Beta project to measure it.
- **No 30-day rolling-window SLO compliance claim is made for any path.**
  Every cloud-path number above is a single bounded burst/sample (FORNX-211:
  ~3.5 minutes, 300 requests), not a soak test. A single clean run cannot
  rule out intermittent failure modes (cold starts, deploy windows,
  elevated load) a longer soak would surface.
- **The cloud-side DLQ (FORNX-212) is live on both Beta and Production.**
  Applied and independently verified via `gcloud` against real
  infrastructure: the dead-letter topic/subscription exist, the ingest
  subscription's `deadLetterPolicy` is set (5 max delivery attempts), and
  both environments' Cloud Run services were confirmed healthy immediately
  after apply. (Note: the merged `fornax-infra` Terraform for `envs/beta`
  is dead code — the real `fornax-beta` GCP project was deleted in a
  migration; the Beta DLQ was actually applied via the correct live repo,
  `horonomy-lab`'s `products/fornax/beta` Terraform.)
- **Non-critical-telemetry sampling is wired but inert.** The default
  sample rate is 1.0 (keep everything) everywhere; nothing is actually
  being dropped in production today. The mechanism exists so a future,
  real backlog-pressure signal has somewhere to act, not because anything
  is being sampled now.
- **The HTTP `/v1/ingest` route does not share the Pub/Sub subscriber's
  sampling policy.** Only the processing leg (the Pub/Sub consumer) has it.
- **Retry-budget behavior under the new DLQ is untested against live
  Pub/Sub** — the Pub/Sub emulator used for local testing does not
  implement dead-lettering, so `max_delivery_attempts` → forward-to-DLQ
  behavior can only be verified once the Terraform above is actually
  applied.
- **Same-user UDS impersonation of a registered sensor remains possible**
  (FORNX-431's own disclosed residual risk, unchanged by this release) —
  the provenance guard authenticates what a message claims about itself
  against a known-sensor allowlist and the session's announced provider;
  it does not authenticate which OS process sent the message. Closing that
  gap needs real runtime attribution (HORO-1599/HORO-1601), out of this
  release's scope by its own dependency note.
- **Direct SQLite file writes bypass the provenance guard entirely** — it
  defends the ingest protocol, not the filesystem.
- **No real human-adjudicated Gold Corpus data exists** (FORNX-343 remains
  founder-paused for cost control, unchanged from v0.0.8) — no calibrated
  real-world accuracy claim is made anywhere in this release.
- **Production monetization stays disabled.** Pricing may show "Coming
  Soon"; no live payment checkout, charging, subscription, or paid
  entitlement activation exists on either the frontend or the backend/API
  paths in this release. Sandbox billing verification remains available.
  This release does not change that posture.

## Capacity and adversarial-corpus status

FORNX-432's independence-capacity benchmark (frozen synthetic fixtures,
explicitly labeled synthetic, not a real workload) found the real cost
driver is genuinely large output size on adversarial shapes
(`rejoining_dag`/`deep_chain`/`adversarial_dense`), not a removable
algorithmic inefficiency — `adversarial_dense` at n=2000 took ~78 seconds
and ~540MB unbounded. The 100,000-work-unit budget now caps this; the
budget's actual calibration and fail-safe mapping per consumer are detailed
in `docs/research/fornx-432-independence-capacity.md` and
`docs/adr/0017-evidence-source-independence.md`.

The adversarial corpus's `fornx380-10` (receipt replay, cross-claim) fixture
— disclosed **Escaped** in v0.0.8 — is now **Prevented** at the
daemon/store layer by FORNX-431's consumption ledger (`docs/security/adversarial-evidence-threat-model.md`
has been updated to reflect this). `fornx380-12` (graph/resource abuse) is
now **Prevented** by FORNX-432's work-budget cap, up from the unbounded-but-
undisclosed state it was in before this release. `fornx380-11` (forged
trust-class label authenticity) remains **Escaped** — unchanged from
v0.0.8, still a sensor/transport-layer gap out of `fornax-verify`'s scope,
tracked separately.

A real follow-up finding from this release's own review process, not fixed
here and not blocking it: `independence.rs`'s union-find `find`/`union`
helpers use plain recursion, empirically confirmed (tested directly on this
build) to risk a stack overflow on a sufficiently deep, uncompressed
derivation chain (fine at 80,000 records, overflows at 90,000+). No
admission-time cap exists on evidence-pool size or `derived_from` chain
length, so this is reachable over the real socket ingest path. Tracked as
FORNX-440, explicitly out of FORNX-432's scope (which bounds the
independence-construction *work*, not union-find recursion depth — a
different mechanism).

## Security

No unresolved Critical/High privacy/security/integrity blocker is known in
the code merged this release. Every finding surfaced during this release's
own review process was either fixed and independently re-verified before
merge (a genuine budget-check-granularity gap in FORNX-432's work-budget
implementation, caught in code review before merge, fixed, and proven via
a new regression test) or explicitly disclosed above/filed as a tracked
follow-up (FORNX-439's production DR gap, FORNX-440's stack-overflow risk).
Nothing was silently accepted as a passing grade.

## Migration notes

All new surfaces (the provenance/consumption ledger, the capacity-budget
cap, the local quarantine table, cloud-side telemetry sampling) are
additive. No breaking changes to existing `Evidence`, `Finding`, `Fusion`,
or policy contracts from prior releases. One real, disclosed behavior
change: FORNX-431's cross-claim replay rule means re-asserting "tests still
pass" in a later turn — without re-running the test — now downgrades to
`Review` instead of verifying against stale evidence from an earlier turn.
This is deliberate (closing exactly the gap FORNX-431 exists to close), not
a regression, and is called out explicitly in `docs/adr/0024-evidence-ingress-provenance-and-consumption.md`
so it isn't discovered by surprise.

## Known limitations

- Production/Beta database PITR does not work today (see "What this
  release does not claim" above) — FORNX-439 remains open.
- Jira governance metadata for this release (a native Fix Version object
  matching this release's exact name, and any native Goal construct) could
  not be created by this campaign — creating a Jira project Fix Version
  requires project-admin rights not exposed by the available tooling
  (FORNX-430, owner-blocked, decision packet already delivered).
  FORNX-433/437/438 (native-ingress adversarial acceptance and the Stage
  7A integrated gate) remain blocked on separate live-attribution
  prerequisites (HORO-1712/HORO-1601), not on anything in this document.
- Pub/Sub message-age, cloud-side DLQ live behavior, and 30-day SLO
  compliance remain unmeasured, per above.
- FORNX-440 (union-find stack-overflow risk) is a disclosed, unfixed
  follow-up.
- See `docs/release/v0.0.8-release-notes.md`'s own carried-forward items
  for anything not superseded by this release (Gold Corpus, federated
  calibration research status).

## Website impact review

`horonomy/fornax-website`'s actual source (public repo, backs
`fornax.horonom.com`) was searched directly for every overclaim pattern
below — `multi-region`, `high-availab*`, `99.9`/SLA/uptime, `disaster
recovery`, `HA`, `enterprise-grade`, `zero-downtime`, `battle-tested`,
`trusted by`/`used by`. **Zero matches.** The Security page already states
plainly that Fornax is MVP/Beta maturity, not GA, and documents real
limits rather than claiming scale/HA/DR. No website edit is required for
this release; the constraints below are the standard to hold future
edits to, not a to-do list against today's content:

- Do not claim a production disaster-recovery capability, a specific
  production RPO/RTO, or "point-in-time restore" for the hosted service —
  not proven for `production`/`beta` (see above).
- Do not claim multi-region availability, high-availability failover, or
  any SLO compliance measured over a real rolling window — none exists.
- Do not claim a specific production throughput/capacity ceiling — FORNX-211's
  numbers are a single bounded sample, not a load-tested ceiling.
- Any public reliability/SLO language should cite only: the ingest/`/readyz`/
  SaaS-availability numbers in FORNX-211's results doc, explicitly labeled
  as a single bounded sample against Beta, not Production, and not a
  rolling-window compliance claim.
- Pricing page (`src/pages/Pricing.tsx`) already satisfies the monetization
  posture above: no live checkout/payment integration, Beta tier price
  explicitly labeled "TBD"/a hypothesis not an offer, Enterprise is
  contact-only, every paid tier requires owner commercial approval before
  it becomes real.
