# Fornax v0.0.9 — Operational Scale & Reliability

**Status:** Not yet tagged/executed as a release (FORNX-263 release
execution has not run as of this writing). This document records the real,
independently-verified engineering state of the v0.0.9 candidate so the
release-execution/QA gates (FORNX-262/263/264) have an honest baseline to
work from — it is not itself a release announcement. The Jira Fix Version
`Fornax v0.0.9 — Operational Scale & Reliability` exists as a native Jira
version (FORNX-430, Done; see "Known limitations").

## What this is

Fornax v0.0.9 (Stage 7A, epic FORNX-146, HVDL-15) is a production-hardening
release: it proves (or honestly fails to prove) that Fornax continues to
accept, preserve, explain, and recover critical evidence under
representative load and failure conditions — not new product surface.

- **Evidence-ingress provenance and replay enforcement** (FORNX-431) — the
  daemon's real verdict-persistence choke point (`run_verifiers_and_persist_findings`,
  the one call all three live verdict paths route through) now filters
  evidence through a provenance guard before any verifier sees it, and
  checks a durable consumption ledger before persisting a `Verified`
  finding. A forged trust-class label, an unregistered sensor, a session
  claiming the wrong owning provider, and a claim reusing evidence already
  consumed by an unrelated claim are all quarantined or downgraded to
  `Review`, never silently verified. Independently re-verified against the
  live daemon under real concurrency (FORNX-435): forged sensor trust,
  foreign-session/provider mismatch, sequential and *concurrent*
  cross-claim replay, a legitimate positive control, and same-claim retry
  idempotency all hold. See `docs/adr/0024-evidence-ingress-provenance-and-consumption.md`.
- **Evidence-independence capacity bounding** (FORNX-432) — the
  evidence-family construction pass disclosed in v0.0.8 as an
  `O(n² log n)` scalability limitation is now benchmarked on frozen
  synthetic adversarial fixtures, sped up 10–143x on common shapes with
  byte-identical output (proptest-proven against a frozen reference
  oracle), and bounded by a deterministic 100,000-work-unit budget that
  aborts construction rather than completing on a poisoned pool — fusion
  fails safe to `Review`, contract satisfaction to `Unknown`, receipt
  issuance refuses outright, and the daemon runs the bounded cost via
  `spawn_blocking` so one poisoned session cannot stall a concurrent clean
  one. Independently re-verified (FORNX-436), including a fixture-potency
  negative control proving the guard is structurally load-bearing, not
  dead code. See `docs/research/fornx-432-independence-capacity.md`.
- **Local-daemon critical-evidence quarantine and backpressure**
  (FORNX-212, local-daemon scope) — a malformed or unprocessable ingest
  line is now durably recorded (`ingest_quarantine` table, with retention
  sweep coverage), not just logged and dropped; a real 512-concurrent-event
  load test proves zero loss and bounded drain time against the daemon's
  256-connection inflight cap.
- **Cloud-path capacity measurement** (FORNX-211, cloud-path scope) — a
  real bounded load run against Beta's live stack: 300/300 ingest
  requests succeeded (100%, vs. 99.5% target), `/readyz` 100% (20/20, vs.
  99.5% target), SaaS availability 100% (20/20, vs. 99% target). See
  `fornax-cloud`'s `docs/fornx-211-cloud-path-results.md`. **Update
  (2026-10-11): Cloud Monitoring access into Beta is now confirmed
  available** (read via the Monitoring API directly) — the earlier "no
  access" note above is stale. Pub/Sub message-age itself still has no
  real-traffic measurement on record; the access gap that blocked it is
  closed, the measurement itself has not yet been taken.
- **Cloud-side DLQ and non-critical-telemetry sampling** (FORNX-212,
  cloud-path scope) — Pub/Sub's native dead-letter-topic mechanism is
  live on Beta (confirmed via `gcloud pubsub subscriptions describe`:
  `deadLetterPolicy` set, `maxDeliveryAttempts=5`), and an explicit,
  deterministic, measurable sampling policy exists for the one genuinely
  non-critical message type (`CapabilitiesMessage`), defaulting to 1.0
  (keep everything) since no real backlog-pressure signal exists yet to
  justify dropping anything. **Update (2026-10-11): the forwarding
  behavior itself was proven with a real drill**, not just config
  readback — a deliberately malformed message was published to Beta's
  real `fornax-ingest-events` topic and confirmed forwarded to the
  dead-letter topic after exactly 5 delivery attempts
  (`CloudPubSubDeadLetterSourceDeliveryCount: 5`), with zero data
  persisted from it. Two real session-poisoning bugs were found and
  fixed in the course of this (fornax-cloud PRs #120/#121): a missing
  `db.rollback()` after a persistence failure that would otherwise
  collaterally delay every other message in the same Pub/Sub pull batch,
  and the same gap in the session-organization-mismatch path. The
  dead-letter subscription itself (`fornax-ingest-events-dlq-sub`) has no
  IAM bindings for any service account — only a project owner/editor can
  currently read a forwarded message to verify it landed; not fixed here.
  See `fornax-cloud`'s `docs/fornx-212-cloud-dlq-backpressure.md`.
- **Storage growth and stay-on-Postgres decision** (FORNX-213) — real
  measured growth (~2.1 KB per session bundle, linear through 100,000
  synthetic sessions) and flat, index-backed read-path latency through the
  same range. Decision: stay on Postgres/Neon — nothing measured justifies
  Kafka, ClickHouse, BigQuery, or a split analytical store. See
  `fornax-cloud`'s `docs/fornx-213-storage-benchmark.md`.
- **Database disaster-recovery drill** (FORNX-214) — a real seeded-failure
  drill (synthetic data destroyed, then recovered via Neon snapshot/restore)
  measured RPO ~76 seconds and RTO ~27 seconds, both well inside the <5
  minute targets, with verified FK consistency and safe double-replay
  idempotency. **This drill ran against the Neon project's root branch, not
  against `production`/`beta` directly** — see "What this release does not
  claim" below; this is the single most important caveat in this entire
  document.

## What this release does not claim

- **Production/Beta database point-in-time restore is NOT proven and does
  not currently work.** FORNX-214's drill measured real RPO/RTO numbers,
  but Neon's snapshot/restore mechanism only operates on a project's root
  branch; `production` and `beta` are non-root child branches and cannot be
  directly snapshotted — confirmed live, twice, independently (FORNX-214's
  original finding, re-confirmed current by FORNX-439's follow-up
  investigation). The real mitigation identified (a scheduled `pg_dump`
  outside Neon's branch mechanism) **has been built, merged, and verified
  against a real published container image on a disposable non-production
  Neon branch — but has not been activated in production.** Activation
  needs three owner-only actions (generate the `age` recovery key, store it
  per the documented custody procedure, and run the first `terraform
  apply`) and, after that, a real production restore drill — none of which
  this campaign's credentials/authorization can perform. **Do not read the
  ~76s/~27s RPO/RTO numbers above as a production guarantee — they describe
  the restore mechanism's speed on disposable data, not a demonstrated
  production recovery, and still won't until the real drill runs.**
  FORNX-439 remains open, tracking activation and the drill as a real,
  disclosed release-boundary question rather than a resolved item.
  **Update 2026-10-23:** activation is done and the real production-topology
  restore drill PASSED (newest production backup restored into a disposable
  branch off `production`, exit 0, 45 tables, RTO 100 s for the restore
  mechanism, backup age 2088 s at drill time). Neon point-in-time restore
  of `production`/`beta` is still unavailable, RPO is bounded by the backup
  schedule, and no production RPO/RTO guarantee is made. FORNX-439 is
  closed on that evidence.
- **Pub/Sub message-age (the processing leg's SLI) is unmeasured.** No
  negative result exists either way — this campaign simply never had Cloud
  Monitoring access into the Beta project to measure it.
- **No 30-day rolling-window SLO compliance claim is made for any path.**
  Every cloud-path number above is a single bounded burst/sample (FORNX-211:
  ~3.5 minutes, 300 requests), not a soak test. A single clean run cannot
  rule out intermittent failure modes (cold starts, deploy windows,
  elevated load) a longer soak would surface.
- **The cloud-side DLQ (FORNX-212) is live on both Beta and Production.**
  Applied and independently verified via `gcloud` against real
  infrastructure: the dead-letter topic/subscription exist, the ingest
  subscription's `deadLetterPolicy` is set (5 max delivery attempts), and
  both environments' Cloud Run services were confirmed healthy immediately
  after apply. (Note: the merged `fornax-infra` Terraform for `envs/beta`
  is dead code — the real `fornax-beta` GCP project was deleted in a
  migration; the Beta DLQ was actually applied via the correct live repo,
  `horonomy-lab`'s `products/fornax/beta` Terraform.)
- **Non-critical-telemetry sampling is wired but inert.** The default
  sample rate is 1.0 (keep everything) everywhere; nothing is actually
  being dropped in production today. The mechanism exists so a future,
  real backlog-pressure signal has somewhere to act, not because anything
  is being sampled now.
- **The HTTP `/v1/ingest` route does not share the Pub/Sub subscriber's
  sampling policy.** Only the processing leg (the Pub/Sub consumer) has it.
- **Retry-budget behavior under the new DLQ is untested against live
  Pub/Sub** — the Pub/Sub emulator used for local testing does not
  implement dead-lettering, so `max_delivery_attempts` → forward-to-DLQ
  behavior can only be verified once the Terraform above is actually
  applied.
- **Same-user UDS impersonation of a registered sensor remains possible**
  (FORNX-431's own disclosed residual risk, unchanged by this release) —
  the provenance guard authenticates what a message claims about itself
  against a known-sensor allowlist and the session's announced provider;
  it does not authenticate which OS process sent the message. Closing that
  gap needs real runtime attribution (HORO-1599/HORO-1601), out of this
  release's scope by its own dependency note.
- **Direct SQLite file writes bypass the provenance guard entirely** — it
  defends the ingest protocol, not the filesystem.
- **No real human-adjudicated Gold Corpus data exists** (FORNX-343 remains
  founder-paused for cost control, unchanged from v0.0.8) — no calibrated
  real-world accuracy claim is made anywhere in this release.
- **Production monetization stays disabled.** Pricing may show "Coming
  Soon"; no live payment checkout, charging, subscription, or paid
  entitlement activation exists on either the frontend or the backend/API
  paths in this release. Sandbox billing verification remains available.
  This release does not change that posture.
- **Default-provider `test_result` verification is capped at `Review`, never
  `Verified`.** FORNX-442/ADR 0025: Claude Code's Bash `tool_response` never
  carries a literal exit code (confirmed against a real v2.1.238 transcript),
  and Codex's default `unified_exec` mode is the same shape — both fall
  through to a heuristic-derived exit code, which is deliberately capped
  below `Verified`. The identical bug was found and fixed in `fornax-cloud`'s
  Python port (FORNX-444) — **fixed on main, deployed to Beta 2026-10-11
  (revision `fornax-backend-00006-2nq`); not yet deployed to Production**
  (GitHub Actions' billing block prevents the normal build-push pipeline
  from running; this was a manual out-of-band build+deploy, owner decision
  pending on Production — see FORNX-262). One stale pre-fix `Verified`
  finding remains in Beta's database (computed 2026-08-31, before the fix
  existed) — nothing automatically re-verifies old findings; flagged to the
  founder, not silently left.

  **No test in this repo currently proves a real
  installed provider's native positive reaching `Verified` end-to-end** —
  the one test that reaches `Verified` via a real daemon/adapter round-trip
  (`concurrent_hook_submission.rs`) does so with a synthetic literal
  `exit_code` field that the adapter's own code confirms no real Claude Code
  version sends; it proves daemon-level session-isolation under concurrency,
  not a genuine native-provider positive. Do not cite it as the latter.
- **FORNX-433 AC3's session-scope leak is fixed** (adapters no longer fall
  back to a shared fake `"unknown"` session id; `fornax-store` rejects a
  blank `session_id` at every insert path) — confirmed zero rows exist under
  the legacy `session_id = 'unknown'` bucket in this machine's real
  dogfooding store, so no legacy false-VERIFIED exposure was found. A
  narrower residual remains: a raw UDS client can still write the literal
  string `"unknown"` (only empty strings are rejected), so that bucket isn't
  structurally impossible yet, just empirically absent.
- **FORNX-433 Slice C (agent-scoped claim verification) is deferred, not
  implemented.** An architecture review found the cross-agent leak it would
  guard against is currently hypothetical — no code path mints a claim from
  a subagent's own output today, so `fornax-verify` pooling all evidence in
  a session (the intended "subagent runs tests, main agent reports" pattern)
  is correct, not a leak. Deferred until a real trigger exists.
- **Two FORNX-437 residuals, named rather than assumed covered**: no test
  proves provenance/replay enforcement specifically survives a daemon
  restart (only that an already-computed verdict persists); no behavioral
  test exists for evidence arriving from a disabled adapter (the design is
  structurally safe — the verdict daemon has zero source references to the
  adapter registry — but untested at the integration level).
- **FORNX-434's Stage 7A gate is an honest NO-GO, not a partial pass.**
  FORNX-211's sample sizes (20/20, 300/300) cannot support the SLO targets
  they're measured against at any real confidence level; FORNX-212's DLQ
  config is verified live but its dead-letter *forwarding behavior* has
  never been proven with a real poison-message drill; FORNX-213 (storage/
  cost) is genuinely verified, the strongest of the five. No manifest-pinned
  v0.0.9 release-candidate artifact exists yet — only prose docs.
  **Superseded 2026-10-23:** FORNX-434 and FORNX-438 were closed on
  risk-based acceptance after the production restore drill passed and a
  manifest-pinned candidate exists (`release/v0.0.9-candidate-manifest.json`);
  the sample-size and dead-letter-forwarding items above stay deferred and
  are not claimed.
- **SonarCloud Code Analysis's failure cause on `fornax-cloud` PR #119 was
  not independently confirmed** (private project, no API access) — disclosed
  as unconfirmed when that PR was merged, not assumed billing-related like
  the account-wide Actions block it ran alongside.
- **FORNX-425's GitHub App token-exchange fix has never been observed
  succeeding in a live Actions run** — the fix is merged and locally
  verified, but every repo this campaign touched hit the same account-wide
  Actions billing block, so the real exchange has never actually executed.

## Capacity and adversarial-corpus status

FORNX-432's independence-capacity benchmark (frozen synthetic fixtures,
explicitly labeled synthetic, not a real workload) found the real cost
driver is genuinely large output size on adversarial shapes
(`rejoining_dag`/`deep_chain`/`adversarial_dense`), not a removable
algorithmic inefficiency — `adversarial_dense` at n=2000 took ~78 seconds
and ~540MB unbounded. The 100,000-work-unit budget now caps this; the
budget's actual calibration and fail-safe mapping per consumer are detailed
in `docs/research/fornx-432-independence-capacity.md` and
`docs/adr/0017-evidence-source-independence.md`.

The adversarial corpus's `fornx380-10` (receipt replay, cross-claim) fixture
— disclosed **Escaped** in v0.0.8 — is now **Prevented** at the
daemon/store layer by FORNX-431's consumption ledger (`docs/security/adversarial-evidence-threat-model.md`
has been updated to reflect this). `fornx380-12` (graph/resource abuse) is
now **Prevented** by FORNX-432's work-budget cap, up from the unbounded-but-
undisclosed state it was in before this release. `fornx380-11` (forged
trust-class label authenticity) — **update: closed**, not still Escaped
as an earlier draft of this document said. FORNX-441's
`CollectorAuthority`/`authorize_evidence_source` (the sensor/transport-
layer defense this fixture's own description said the real fix belonged
to) now quarantines it, proven both as a unit test in
`provenance_guard.rs` and against the real live daemon over its real UDS
socket (`provenance_enforcement.rs::forged_host_observed_label_never_reaches_verified`).
See `docs/research/fornx380-corpus-live-ingress-status.md` for the full,
per-fixture disclosure — it concludes no currently-known escape remains
in this corpus. The residual gap that *is* still real and unchanged: same-
user UDS impersonation of a registered sensor (the provenance guard
authenticates what a message claims, not which OS process sent it);
listed separately below.

A real follow-up finding from this release's own review process, not fixed
here and not blocking it: `independence.rs`'s union-find `find`/`union`
helpers use plain recursion, empirically confirmed (tested directly on this
build) to risk a stack overflow on a sufficiently deep, uncompressed
derivation chain (fine at 80,000 records, overflows at 90,000+). No
admission-time cap exists on evidence-pool size or `derived_from` chain
length, so this is reachable over the real socket ingest path. Tracked as
FORNX-440, explicitly out of FORNX-432's scope (which bounds the
independence-construction *work*, not union-find recursion depth — a
different mechanism).

## Security

No unresolved Critical/High privacy/security/integrity blocker is known in
the code merged this release. Every finding surfaced during this release's
own review process was either fixed and independently re-verified before
merge (a genuine budget-check-granularity gap in FORNX-432's work-budget
implementation, caught in code review before merge, fixed, and proven via
a new regression test) or explicitly disclosed above/filed as a tracked
follow-up (FORNX-439's production DR gap, FORNX-440's stack-overflow risk).
Nothing was silently accepted as a passing grade.

## Migration notes

All new surfaces (the provenance/consumption ledger, the capacity-budget
cap, the local quarantine table, cloud-side telemetry sampling) are
additive. No breaking changes to existing `Evidence`, `Finding`, `Fusion`,
or policy contracts from prior releases. One real, disclosed behavior
change: FORNX-431's cross-claim replay rule means re-asserting "tests still
pass" in a later turn — without re-running the test — now downgrades to
`Review` instead of verifying against stale evidence from an earlier turn.
This is deliberate (closing exactly the gap FORNX-431 exists to close), not
a regression, and is called out explicitly in `docs/adr/0024-evidence-ingress-provenance-and-consumption.md`
so it isn't discovered by surprise.

## Known limitations

- Production/Beta database PITR does not work today (see "What this
  release does not claim" above). It is mitigated, not solved, by the
  `pg_dump` backup/restore path, whose production-backup restore drill
  passed on 2026-10-23 (RTO 100 s, backup age 2088 s; FORNX-439 Done).
  RPO is bounded by the backup schedule; there is no operator-latency
  proof and no multi-region or HA claim.
- Jira governance metadata: the native Fix Version for this release exists
  (FORNX-430); a native Goal construct could not be created (no API surface).
  FORNX-433's session-scope-leak fix (AC3 Slice A) is merged; its Slice C
  (agent-scoped verification) stays deferred as a hypothetical-today
  concern, not a live-attribution blocker. FORNX-437 is a partial pass with
  two named residuals (restart, disabled-adapter behavior) and a corrected
  "native positive" scenario (no test proves a real provider reaching
  `Verified`, only daemon-level concurrency correctness). FORNX-438/434 were closed on
  2026-10-23 on risk-based acceptance; the SLO sample-size, Pub/Sub
  message-age and similar items listed above stay deferred and are not
  claimed.
- Default-provider `test_result` verification (Claude Code, Codex default
  mode) is capped at `Review`; see "What this release does not claim" above
  for the full ADR 0025 ceiling and the corrected native-positive scenario.
- Pub/Sub message-age, cloud-side DLQ live behavior, and 30-day SLO
  compliance remain unmeasured, per above.
- FORNX-440 (union-find stack-overflow risk) is a disclosed, unfixed
  follow-up.
- A `fornax-cloud` test (`test_hold_committed_before_delete_starts_is_reliably_caught`)
  has a diagnosed test-robustness gap (a fixed 50ms sleep as a timing proxy
  for "the hold has committed," not a real synchronization signal) — not a
  product correctness bug; the advisory-lock mutual exclusion itself holds
  in both directions. Fix recommended, not applied.
- `fornax-core`'s daemon integration test harness (`provenance_enforcement.rs`
  and others) has a known port-binding race ("Address already in use")
  under this machine's concurrent-session load, and a resource-contention
  timing flake in `fornax-adapter-opencode`'s `live_transport.rs` (daemon
  startup past its fixed 5s poll timeout under load) — both confirmed
  unrelated to any logic change by rerunning in isolation; this is where
  the FORNX-437 "harness flakiness" note resolves to, not a separate
  tracked ticket.
- `fornax-ingest-events-dlq-sub` (Beta's dead-letter subscription) has no
  IAM bindings for any service account — only a project owner/editor can
  currently read a forwarded dead-lettered message to verify delivery;
  found during the FORNX-212 drill, not fixed here.
- `fornax-cloud`'s `main` branch has 4 open Dependabot alerts (3 high, 1
  moderate) as of this release's merges — not triaged in this campaign
  (package, reachability, and bot-PR status unreviewed); blocks the
  release's security-results packet, not current engineering.
- **Data egress.** Nothing leaves the machine until an egress profile is
  chosen (`fornax egress profile-set personal|corporate`). One persisted,
  fail-closed decision (ADR-0027) is asked before every outbound attempt: the
  audit-checkpoint push, the policy poll, the semantic judge and the monthly
  metadata upload; the separate `fornax-cloud` uploader reads a derived
  projection (byte-pinned to its golden fixtures) and stays inert unless that
  projection authorizes it. **A locally selected corporate profile is
  local-only in code**: it never uploads evidence or checkpoints, never
  schedules an upload, and no consent, allowlist entry or environment variable
  overrides it (entering it revokes every consent). This is a per-install
  setting held in the user-writable local database, **not organization-enforced
  policy**: a signed organisation policy's `egress.cloud_sync_allowed` is not yet
  consumed, so this release must not be described as enterprise-enforced
  no-egress. **Personal** uploads only metadata
  (`evidence_metadata`, `finding_verdicts`, `capability_declarations`), only to
  an allowlisted destination, only under a live expiring consent, and only
  while `FORNAX_CLOUD_SYNC_ENABLED=1`; claim text and evidence payloads are
  never uploadable and no client follows redirects.
- **Monthly metadata upload (personal profile).** With a live
  `evidence_batch_upload` consent the daemon sends each closed month
  automatically (hourly tick, inert without a consent, a device id and a 0600
  credential file); `fornax upload status|preview|run` is the manual path.
  Eligible records are copied into a local outbox ahead of the 30-day
  retention sweep, batches are sealed with a persisted hash, retries resend
  identical bytes under the same idempotency key, a crash or lost response
  resumes the same batch, and records that can never be sent (consent ended,
  50 MiB / 90-day outbox bound) are recorded as visible gaps. Receiver:
  `fornax-cloud` `POST /v1/metadata-batches` (exact key allowlist, bounded
  values, hash re-check, per-device dedup). **Behaviour changes:**
  `FORNAX_CLOUD_SYNC_ENABLED=1` alone no longer enables the checkpoint push and
  `FORNAX_POLICY_POLL_URL` alone no longer polls (each needs an allowlist
  entry). **Not enforced:** policy lives in the user-writable local database, so
  a local user who edits it can bypass it; a signed policy's
  `egress.cloud_sync_allowed=false` is not yet folded into the decision;
  `export-spool` stays manual with no integrity manifest; findings keep their
  rationale text for their own retention window after the raw evidence is
  purged; local legal hold, a cloud retention floor and a local deletion
  command are not implemented. **Interrupted uploads:** the upload lock
  (`$FORNAX_HOME/upload.lock`) is taken for the duration of a run; if the
  process is killed mid-run the lock survives and the next manual run is
  refused as busy until it is 30 minutes old (or you delete it when you know
  nothing is running). The daemon retries hourly, so a monthly upload resumes by
  itself within about 90 minutes; the interrupted batch stays sealed and is
  resent byte-identically, so no data is lost or duplicated. Tracked in
  FORNX-464.
- **Retention sweep.** The sweep used to fail every cycle with a foreign-key
  error once findings or soft-purged evidence referenced old events, so nothing
  was ever purged on realistic data; it now purges content in place when a row
  cannot be deleted (FORNX-467).
- **Identity scope.** Session attribution is per provider-native session
  (Claude Code hook `session_id`; Codex hook and rollout `session_meta`);
  unknown stays unknown, and a blank id is treated as absent. Subagent
  `agent_id`/`agent_type` (Claude) and `turn_id` (Codex) are persisted per event
  and returned on findings; lineage is always `unknown` because no provider
  exposes a parent link. Evidence is still pooled per session by design, so a
  second agent's passing evidence in the same session can verify the first
  agent's claim (disclosed in `fornax doctor`). `fornax status`, `fornax detail`
  and the legacy status-line wrappers show the newest finding across **all**
  sessions on the host and say "(host-wide)"; the session-scoped surface is
  `fornax statusline provider`. Rows written before FORNX-433 under the
  placeholder session `"unknown"` are flagged `legacy_unattributed`; events
  stored before the attribution migration stay unattributed (no backfill).
  fornax-cloud binds a session to the device that opened it (FORNX-463): another
  device in the same organisation is refused. The loopback API is
  unauthenticated for same-user processes. `bind_host_event` output can be
  persisted with its canonical identity (`Store::insert_bound_host_event`), but
  no host ingress is wired to it yet. Tracked in FORNX-465/466/463.
- **Codex rollout tailer.** `fornax-hook-codex` forwards nothing until the
  rollout's `session_meta` supplies a native session id (FORNX-462); it no
  longer falls back to the file path. Verified against codex-cli 0.163.0
  through one bounded real `codex exec` session using a local model; Codex
  native hook activation and the OpenAI-hosted-model path are not verified
  (FORNX-457).
- **Claude hook configuration.** `fornax install claude-code` records which
  empty hook structures already existed in a hidden
  `.settings.json.fornax-state` file next to `settings.json` (only when
  there is something to record) so `uninstall` restores them (FORNX-460); a
  record left stale by a downgrade can leave one empty array behind.
- See `docs/release/v0.0.8-release-notes.md`'s own carried-forward items
  for anything not superseded by this release (Gold Corpus, federated
  calibration research status).

## Website impact review

`horonomy/fornax-website`'s actual source (public repo, backs
`fornax.horonom.com`) was searched directly for every overclaim pattern
below — `multi-region`, `high-availab*`, `99.9`/SLA/uptime, `disaster
recovery`, `HA`, `enterprise-grade`, `zero-downtime`, `battle-tested`,
`trusted by`/`used by`. **Zero matches.** The Security page already states
plainly that Fornax is MVP/Beta maturity, not GA, and documents real
limits rather than claiming scale/HA/DR. No website edit is required for
