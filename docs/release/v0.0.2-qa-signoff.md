## What was verified live this pass

All of the following were exercised against the real deployed
`fornax-backend` Cloud Run service (via `gcloud run services proxy`, since
`allow_unauthenticated=false` by design — see "What was not verified"):

**Device lifecycle (real HTTP, real Postgres, real IAM boundary):**
- Register → 201, issues a real credential.
- Duplicate registration of the same `device_id` → 409 (create-only, no
  silent rotation).
- Malformed registration (empty `device_id`) → 422.
- Rotate with the wrong credential → 401 (proof-of-possession enforced).
- Rotate with the real credential → 200, issues a new credential.
- The just-rotated-out credential → 401 (old credential invalidated).
- Revoke with the current credential → 200.
- The just-revoked credential → 401 (revocation enforced).

**Ingest → persist → verify pipeline (real HTTP, real Postgres, real async
worker):**
- A full batch (capabilities + event + evidence + claim, `subject:
  "test_result"`, `exit_code: 0`) → 202 accepted, session created, and the
  in-process verifier worker computed a real `verdict: verified` finding
  within its 2s poll interval — confirmed via `GET /v1/findings`.
- **Found and fixed live** (FORNX-369): a claim referencing a
  `source_event_id` not yet known to the server crashed with an unhandled
  500 (`asyncpg.ForeignKeyViolationError`) — contradicts this router's own
  documented tolerance for out-of-order batch delivery. Root-caused, fixed
  (persist_batch now catches the IntegrityError and returns 400), regression
  test added (`test_ingest_rejects_claim_referencing_unknown_event_with_400_not_500`,
  also proves the session recovers for the next request), verified locally
  (598 passed/9 skipped/0 failed) and re-verified live against the redeployed
  fix: same request now returns 400, and a follow-up well-formed batch on the
  same credential still succeeds (202) — see fornax-cloud PR #78.
- Cross-tenant/cross-device isolation, replay-resistance (OIDC state/nonce),
  CSRF protection, credential-never-logged negative paths, rate limiting,
  redaction at write time: covered by the existing automated suite, run
  against real Postgres this pass — 598 passed, 9 skipped (pre-existing,
  need a local Pub/Sub emulator or Keycloak instance, not run this pass),
  0 failed. `ruff format`/`ruff check`/`mypy` all clean. Rust workspace
  (`fornax-ingest`, `fornax-uploader`): 91 passed, clippy clean. Frontend:
  86/86 tests, typecheck/lint clean.
- Historical evidence (not re-run, but real and dated 2026-08-31, found in
  Cloud Logging): a prior "golden-journey" pass exercised the same pipeline

## What was NOT verified — genuine remaining gaps

- **No literal Claude Code/Codex session was driven through this pipeline.**
  All ingest payloads this pass were hand-constructed JSON matching the
  wire schema, not captured from a real running coding-agent session.
  FORNX-64's "real BETA READY gate using actual Claude Code and Codex
  traffic" is not satisfied by this pass.
- **No public self-service registration path exists to test.**
  `backend_service.allow_unauthenticated` stays `false` by explicit design
  (pending FORNX-137's trust-model cutover) — every check above required a
  temporary, self-granted `run.invoker` binding, immediately revoked after
  use. A genuine "fresh user, no prior access" journey cannot be run until
  that cutover happens.
- **Egress/redaction security-negative sweep not run this pass**: no
  synthetic-secret injection test, no XSS/injection payload test against
  claim/evidence text fields, no SIEM export negative-path test (the
  SIEM feature itself was only just migrated into this environment — see
  FORNX-370).
- **No load/retry/offline-recovery test against the real network path** —
  only single-request correctness was checked, not sustained traffic,
  timeout/retry behavior, or Cloud Run cold-start-under-load.
- **Frontend/dashboard not exercised against this live backend** — the
  86/86 frontend tests run against a local dev harness, not this deployed
  API.
