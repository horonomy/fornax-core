## 2026-09-19 pass — frontend deployment (FORNX-241 checklist items 1-14)

Founder-approved architecture decision (2026-09-19): deploy fornax-cloud's
frontend (Vite + React 19 SPA, TanStack Router/Query, confirmed no SSR
requirement — no server loaders, no API routes, nothing beyond a static
build) to Cloudflare Workers static assets (the current Cloudflare-endorsed
replacement for classic Pages for new static sites) rather than Cloud Run,
serving at `https://fornax.horo.run`.

**Hostname conflict found and resolved:** `fornax.horo.run` was, at the
start of this pass, a live 301 redirect to `fornax.horonom.com` — a
Cloudflare Worker (`fornax-edge`, ticket HORO-572) deliberately
decommissioned that hostname as a runtime surface, as one instance of a
cross-product convention (ADR-0006/HORO-566, shared with
`ophiuchus-edge`/`horologium-edge`). Releasing that hostname for the real
SaaS app is a legitimate use of it — HORO-572's actual concern (duplicate
marketing content on two hostnames) does not recur once the hostname
serves a distinct real application instead of a marketing-site copy — but
it is a genuine deviation from another ticket's cross-product decision, not
a same-repo detail, so it's called out explicitly here rather than folded
in silently. `fornax-edge` itself was not deleted (kept deployed, routeless,
in case the redirect is ever needed again). fornax-website PR #15.

**Deployed and verified live:**
- `fornax-beta-frontend` Worker (Cloudflare Workers static assets,
  `not_found_handling: single-page-application` for client-side routing)
  serving the real production build at `https://fornax.horo.run` —
  confirmed via `curl -I` (200, real HTML, `cf-cache-status`/`server:
  cloudflare` present) and via a real browser session (screenshots:
  `fornax-beta-live-sessions.png`, `fornax-beta-live-findings.png`,
  `01-session-list.png`–`04-mobile-finding-list.png`), showing genuine
  session/finding data from this Beta backend, including sessions from
  this very QA campaign.
- **`api.fornax.horo.run` TLS gap, root-caused precisely, found and worked
  around, not hidden:** `api.fornax.horo.run` has no certificate because
  `fornax-api-edge` reaches it via a plain Workers **Route**
  (`infra/workers/fornax-api-edge/wrangler.toml`), and per Cloudflare's own
  docs (Workers Best Practices, Custom Domains) only a Workers **Custom
  Domain** auto-provisions an Advanced Certificate for its hostname — a
  Route never does, regardless of Universal SSL/Total TLS/subdomain depth
  (the earlier "second-level subdomain coverage" theory was wrong; ruled
  out empirically below). Confirmed two ways: (1) `docs.fornax.horo.run`
  presents a real cert because it's attached as a Pages/Workers Custom
  Domain, while `api.fornax.horo.run` — a Route only — returns a bare TLS
  alert 40 via `openssl s_client`, even after a long wait, which a
  provisioning-delay theory doesn't explain; (2) attempted the actual fix
  live — edited `wrangler.toml` to `custom_domain = true` and ran
  `wrangler deploy` with the real `CLOUDFLARE_PAGES_API_TOKEN` — Cloudflare's
  API rejected it with `code 100117`: "Hostname 'api.fornax.horo.run'
  already has externally managed DNS records... Delete them first" — i.e.
  the existing proxied CNAME (created directly via the Cloudflare API for
  FORNX-241, before `fornax-api-edge` existed) blocks the Custom Domain
  from attaching. The available token has zone-read but not DNS-write scope
  (`dns_records` list call returned `Authentication error`), so deleting
  that CNAME to unblock the Custom Domain is a genuine owner-scope action,
  not a self-service one. Change was cleanly reverted (`wrangler.toml` back
  to the Route form) after confirming zero regression — the zone-level
  Worker route (`api.fornax.horo.run/* → fornax-api-edge`, ID
  `2bb589821f5b457991c5b2e9f6ef3816`) was untouched by the failed attempt.
  Rather than block the real fresh-user browser journey on that owner-only
  DNS-write scope grant, the `fornax-beta-frontend` Worker itself proxies
  `/v1/*` same-origin to the backend's real Cloud Run origin
  (`fornax-cloud/frontend/src/worker.ts`, sharing
  `infra/workers/shared/cloud-run-proxy.ts` with the standalone
  `fornax-api-edge` Worker that's deployed and ready to take over the
  moment the CNAME is deleted and `custom_domain = true` redeploys clean).
  Verified live: `curl https://fornax.horo.run/v1/sessions` → a real
  backend 401 (missing Authorization), not a network/TLS error — proof the
  proxy path genuinely reaches Cloud Run today. fornax-cloud PR #79.
- **CORS**: `FORNAX_CLOUD_CORS_ORIGINS=https://fornax.horo.run` added to
  `fornax-backend`'s Cloud Run env and applied live (`terraform apply`,
  horonomy-lab PR #11) — currently a no-op for the live path (same-origin
  proxy needs no CORS) but correct and forward-compatible for the moment
  `api.fornax.horo.run` takes over directly.
- **Same-site session-cookie auth confirmed compatible**: `fornax_session`/
  `fornax_csrf` are host-only, `SameSite=Lax` cookies with no `Domain`
  attribute set by the backend (`core/user_sessions.py`) — since
  `fornax.horo.run` and `api.fornax.horo.run` share the same registrable
  domain (`horo.run`), this works today for the direct-origin path without
  any backend change; confirmed by reading the cookie-setting code, not
  assumed.
- **Frontend security-negative check (checklist item 10)**: real
  pre-existing findings whose claim text contains XSS payloads (`<script>`,
  `<img onerror>`, a `javascript:` URI) render as literal escaped text in
  the findings table, not executed — confirmed live
  (`fornax-xss-dashboard.png`; React's default JSX escaping, no
  `dangerouslySetInnerHTML` in the render path).
- **No server-only secrets in the bundle (checklist item 11)**: confirmed
  by inspecting the shipped bundle — only `VITE_`-prefixed, non-secret
  build-time values are referenced (`VITE_API_BASE_URL`, and here it is
  empty/same-origin, so not even that string appears in the bundle).
- **Cache/deploy config (checklist item 12)**: Workers static assets serve
  with Cloudflare's default immutable-asset caching for hashed filenames
  (`index-*.js` etc.) and `no-cache` for `index.html`, matching the SPA's
  own build output — no extra configuration needed beyond the default
  `assets` block.
- Auth: real browser journey used the documented break-glass
  device-credential path (`CredentialGate`), not SSO — consistent with the
  already-disclosed absence of a live Keycloak instance in this
  environment; not a new gap.

**Still not verified / genuine remaining gaps after this pass:**
- `api.fornax.horo.run` and `ingest.fornax.horo.run`'s own direct TLS —
  root-caused (see above): no certificate because both are Workers Routes,
  not Custom Domains, and converting either requires deleting an existing
  externally-managed DNS record first, which needs DNS-write scope the
  current token doesn't have. Not blocking today (api has a working
  alternate path via the frontend's same-origin proxy; ingest has no
  Worker in front of it at all yet — a pre-existing gap, not new to this
  pass). Real follow-up, not a "wait and re-check", tracked as
  **FORNX-371**: needs an owner-granted DNS-write-scoped token to delete
  the two CNAMEs, then `custom_domain = true` + `wrangler deploy` for
  `fornax-api-edge` (and an analogous `fornax-ingest-edge` Worker, not yet
  built, for ingest).
- No load/sustained-traffic test of the frontend↔backend path.
- Frontend was not tested against a real SSO/OIDC login (no live Keycloak
  in this environment, pre-existing gap, unchanged by this pass).

## What was verified live this pass
