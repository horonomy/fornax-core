# Fornax v0.0.3 — Extensible Evidence Platform — Release Notes

**Status:** engineering complete, release candidate. Epic FORNX-138 and all
its children (FORNX-155–162, FORNX-289–293) are Done. QA/Security sign-off
(FORNX-244) is **Done, PASS** — see `docs/release/v0.0.3-qa-signoff.md` and
`docs/release/v0.0.3-security-signoff.md`. There is still no frozen
candidate manifest or tag yet — the release itself (FORNX-245) has not run.
This document will be updated with that evidence once FORNX-245 completes;
see `docs/release/release-docs-governance.md` for the docs-gate process
this release follows.

## What this is

Fornax v0.0.3 does not add a new user-facing capability on top of v0.0.1's
core loop (`observe → extract claim → verify → report`, still five honest
verdicts, still local-first with no cloud dependency on the critical path).
It answers a different, structural question: **can a new provider or a new
kind of evidence be added to Fornax without rewriting core domain logic?**

The answer, demonstrated rather than asserted: yes. This release generalizes
the two-provider (Claude Code, Codex) capability/evidence model into an
explicit, versioned extension contract, then proves that contract by adding
a third, architecturally distinct provider — opencode CLI — through it.

## Why extensibility matters here

Fornax's core promise (checking an agent's claims against captured evidence)
is only as credible as its evidence pipeline is honest about what each
provider can and can't expose. Before this release, "what a provider can
expose" was six fixed booleans and evidence collection was ad hoc code
inline in each adapter. That worked for two providers whose integration
mechanisms happened to be somewhat similar (external hook process; file
tail) — it would not have scaled cleanly to a third with a genuinely
different mechanism, and it gave no accepted place for provider-specific
evidence to live without either forcing it into a premature "canonical"
field or throwing away its structure entirely.

This release replaces that with:

- An open, three-state signal taxonomy (`Available` / `Unsupported` / `Unavailable`,
  plus `Unknown` for "not yet assessed") instead of six fixed booleans —
  see `docs/research/adapter-capability-matrix.md`.
- A uniform `EvidenceSensor`/`EvidenceSource` contract with named trust
  classes and structured provenance (collection method, freshness, tamper
  boundary) — see `docs/research/evidence-sensor-contract.md`.
- A versioned, opt-in `ExtensionEnvelope` for genuinely provider-specific
  evidence, with an explicit promotion-to-canonical path and a documented
  deprecation ritual — see `docs/adr/0005-schema-evolution.md`.
- A practical, worked checklist for adding a new adapter —
  `docs/contributing/adding-an-adapter.md`.

## The third-provider proof: opencode CLI

**opencode** (open-source, TypeScript, provider-agnostic) was selected and
integrated as an architecture-fitness test, running against a local Ollama
backend at zero API cost. It is a genuinely different integration mechanism
from both existing adapters: an in-process plugin the provider's own runtime
loads and invokes directly, rather than an externally spawned hook process
(Claude Code) or a tailed transcript file (Codex).

**Headline finding:** adding `Provider::OpenCode` and running
`cargo check`/`cargo clippy --workspace --all-targets -- -D warnings` found
**zero unexpected core coupling** — no file in `fornax-daemon`,
`fornax-store`, or `fornax-verify` needed to change to add a third provider.
opencode's exit-code signal (`tool.execute.after`'s `output.metadata.exit`)
is also a first for Fornax: a literal, non-heuristic exit code, where both
existing adapters rely on a heuristic (Claude Code) or a provider-shape-
dependent partial signal (Codex).

The transport leg — plugin → adapter binary → daemon over a Unix domain
socket — was built in the same ticket but explicitly disclosed as *not yet
run end-to-end*. A follow-on ticket (FORNX-291) closed that gap: a real
opencode session was driven through the real shipped plugin file, the real
`fornax-hook-opencode` binary, and a real running daemon, with the daemon's
own on-disk SQLite store inspected afterward as independent proof of
receipt. That work found and fixed one real bug (an unhandled error on the
spawned child process could crash opencode itself, not just the capture
pipeline) and left a permanent CI regression
(`crates/fornax-adapter-opencode/tests/live_transport.rs`); a second ticket
(FORNX-292) fixed a flaky assertion in that same test's polling logic. See
`docs/research/0003-opencode-live-transport-verification.md` for the full
evidence trail.

## Exact supported scope

| Provider | Status | Primary integration mechanism |
|---|---|---|
| Claude Code | Supported | External hook process (`PreToolUse`/`PostToolUse`/`Stop`/`SessionStart`/`SubagentStart`/`SubagentStop`) |
| Codex CLI | Supported, real capability gaps vs. Claude Code | Rollout-file tailing (hooks are opt-in/admin-suppressible, secondary at best) |
| opencode CLI | **Experimental** — architecture-fitness proof, not production-hardened parity with the other two | In-process plugin, spawning a long-lived companion binary over stdin |

See `docs/research/adapter-capability-matrix.md`'s "Consolidated
compatibility matrix" for the exact, code-grounded per-signal support table
across all three providers — do not assume symmetry between any two of
them.

**Known, disclosed limitations of the opencode integration** (not silently
rounded up to "supported"):

- Fully autonomous local-Ollama tool-calling under opencode's real
  production-size system prompt does not work reliably on any model tested
  — both the fixture-capture work and the live end-to-end proof stand a
  deterministic stub in for only the LLM's own turn. Everything downstream
  of that one stubbed response (the real process opencode spawns, its real
  exit code, every hop through the real plugin/binary/daemon) is genuine,
  unstubbed code.
- `FinalResponse` is `Unavailable`: the real event stream carries it, this
  adapter version doesn't yet translate it.
- `SubagentLifecycle` is `Unsupported`: no such hook exists in opencode's
  Hooks interface at all.
- `fornax export-spool` of an opencode session will be rejected (HTTP 422)
  by `fornax-cloud`'s ingest API today — that repo's ingest boundary still
  enforces a closed, 2-variant `Provider` enum. Local monitoring is
  unaffected; cloud sync of an opencode session is not yet supported.

**Not shipped, and not implied by this release:** a plugin marketplace, a
dynamic/runtime extension-loading system, or general third-party adapter
distribution. opencode is one concrete, demonstrated integration built and
shipped by this project, proving the architecture generalizes — not a
mechanism for arbitrary external code to attach to a running Fornax daemon.

## Security review findings (FORNX-244) — both fixed before release

Found and fixed during this release's QA/Security sign-off pass, not
shipped as known limitations:

- **`ExtensionEnvelope` redaction bypass** (SEC-v0.0.3-0001):
  `fornax-daemon`'s redaction boundary (`docs/privacy-redaction-policy.md`)
  scanned `Evidence::payload` before persistence but not
  `Evidence::extension`. `ExtensionEnvelope::fields` is deliberately
  untyped, provider-specific JSON — this release's opencode adapter is the
  first real producer of one (tool-call title/timing telemetry) — so this
  was a real, structural gap. Fixed: `redact_json` now applies to
  `extension.fields`/`.unknown` the same way it already applied to
  `payload`.
- **Cross-provider capability-cache spoofing/downgrade**
  (SEC-v0.0.3-0002): `fornax-daemon`'s in-memory capabilities cache was
  keyed only on provider-controlled `session_id`, so a same-session
  announcement from a different provider could silently overwrite another
  provider's cached capabilities — a real downgrade path that could
  suppress verification. Fixed: a cross-provider overwrite of an
  already-cached session is now refused.

See `docs/release/v0.0.3-security-signoff.md` for the full findings,
evidence, and regression tests.

## Migration notes

**Nothing in this release breaks an existing v0.0.1 adapter, client, or
on-disk record.** Every schema change is additive:

- `runtime_capabilities` gained nullable `schema_version`/`signals` columns
  (`0003_capability_signals.sql`); the original six boolean columns are kept,
  not dropped.
- `evidence` gained nullable `source` (`0004_evidence_source.sql`) and
  `extension` (`0005_evidence_extension.sql`) columns.
- Every new field added to an existing struct across this release
  (`EvidenceSource`'s `collection_method`/`collector_version`/`freshness`/
  `tamper_boundary`, `Evidence::extension`) either defaults to `None` or to
  an explicit, honestly-named "unknown"/"pre-provenance" value on
  deserialize — never a fabricated-looking guess. No existing row needs
  backfilling and no existing consumer needs to change to keep working.
- No adapter's public trait surface (`AgentAdapter`, `CapabilityProbe`)
  changed shape; `Provider` gained a third variant (`OpenCode`) additively —
  FORNX-161 confirmed `cargo check`/`clippy --workspace` pass with zero
  changes required outside `fornax-types` itself.

`$FORNAX_HOME`'s on-disk schema stability caveat from the `v0.0.1` release
notes is unchanged by this release: these migrations were verified additive
on top of a schema that already includes the `v0.0.1`-era tables, not
independently re-verified against an untouched `v0.0.1` database file. If in
doubt, the `v0.0.1` guidance still applies — back up or discard
`$FORNAX_HOME` before upgrading.
