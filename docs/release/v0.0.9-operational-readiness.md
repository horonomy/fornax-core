# Fornax v0.0.9 — operational readiness checklist (FORNX-225)

Maps each of FORNX-225's "Required Updates" categories to its real evidence
source. Every number here is traceable to a specific doc or test cited
below — nothing is restated from memory or rounded up. See
`docs/release/v0.0.9-release-notes.md` for the narrative summary and the
full "what this release does not claim" list; this document is the
checklist form.

## SLI/SLO/error-budget definitions

Source of truth: `fornax-infra`'s `infra/docs/slo-definitions.md` (FORNX-210)
defines four paths (local sync, ingest, processing, SaaS availability),
each with an SLI, a target, and what counts against the error budget. That
document states plainly it does not claim the targets are currently met —
FORNX-211 is what generated the first real measurement against them.

| Path | Target | Measured | Status |
|---|---|---|---|
| Local sync (adapter→persisted-evidence latency) | p99 < 500ms | not measured against production traffic | ⚠️ no data |
| Ingest HTTP success rate | 99.5% (valid requests) | 100% (300/300), single ~3.5min burst | ✅ above target, bounded sample only |
| Processing: Pub/Sub message-age p95 | < 60s | not measured (no Cloud Monitoring access into Beta) | ⚠️ no data |
| Processing: `/readyz` success rate | 99.5% | 100% (20/20) | ✅ above target, bounded sample only |
| SaaS availability (`fornax.horo.run`) | 99% | 100% (20/20) | ✅ above target, bounded sample only |

None of the ✅ rows constitute a 30-day rolling-window compliance claim —
each is one bounded sample. See `fornax-cloud`'s `docs/fornx-211-cloud-path-results.md`
for the full run detail and its own explicit caveats.

## Capacity/load/soak methodology and tested limits

Source: `docs/research/fornx-432-independence-capacity.md` (fornax-core,
evidence-independence construction) and `fornax-cloud`'s
`docs/fornx-211-cloud-path-results.md` (cloud ingest/processing/SaaS path).

- Methodology: frozen, deterministic synthetic fixtures (`flat`,
  `agent_turn_fanout`, `wide_derived_fanout`, `rejoining_dag`, `deep_chain`,
  `adversarial_dense`), explicitly labeled synthetic
  (`contains_synthetic_labels: true`), cross-checked against a frozen
  reference implementation for output correctness, not just speed.
- Tested limit found: `adversarial_dense` at n=2000 costs ~78s wall /
  ~540MB peak unbounded — this is genuinely large output, not a removable
  inefficiency (sped up only ~1.0x by the FORNX-432 PR 2 optimization pass,
  vs. 10-143x on the cheap shapes). Now capped by a 100,000-work-unit
  deterministic budget (`FamilyBudget::DEFAULT_MAX_WORK_UNITS`).
- This is **not** a soak test. FORNX-211's cloud-path run was a single
  ~3.5-minute, 300-request burst against Beta, explicitly stated by its own
  results doc as "not a 30-day rolling-window SLO compliance claim."

## Backpressure, retry, DLQ/poison-event handling, replay/idempotency, critical-vs-noncritical loss policy

Source: fornax-core (local-daemon scope, merged PRs #227/#228/#231) and
`fornax-cloud`'s `docs/fornx-212-cloud-dlq-backpressure.md` (cloud scope).

- **Local daemon**: a malformed/unprocessable ingest line is durably
  recorded in an `ingest_quarantine` table (with retention-sweep coverage),
  not silently dropped. A real integration test fires 512 concurrent
  events (2x the daemon's 256-connection inflight cap) over the real UDS
  path and proves zero loss within a bounded drain time.
- **Cloud DLQ**: Pub/Sub's native dead-letter-topic mechanism is wired via
  Terraform for both Beta and Production (`dead_letter_topic_id`,
  `max_delivery_attempts=5`), plus the IAM grants Google's own mechanism
  needs. **Code-only — not applied to live infrastructure.** Applying it
  is an explicit owner decision this campaign's GCP credentials cannot
  make (no project access).
- **Non-critical telemetry sampling**: explicit, deterministic (not
  random), measurable — `CapabilitiesMessage` is the only message type
  classified non-critical; the whole verdict chain (events/claims/evidence/
  links/missing-evidence/decisions) is never eligible. Default sample rate
  1.0 (keep everything) everywhere — nothing is being dropped in
  production today; the mechanism exists for a future real backlog signal.
- **Replay/idempotency**: `routers/ingest.py::persist_batch` already keys
  every message type on its own envelope UUID via `ON CONFLICT DO NOTHING`
  (or a `(device_id, provider)` upsert for `CapabilitiesMessage`) — a
  replayed batch is already a safe no-op, confirmed by re-reading the
  code, no new code needed.
- **Evidence-independence work-budget fail-safe mapping** (the
  provenance/capacity-adjacent "critical loss" policy): fusion fails safe
  to `Verdict::Review`, contract satisfaction to `SatisfactionState::Unknown`,
  voi to `Independence::Unverified`, receipt issuance refuses outright —
  never a partial/truncated result, which would be the unsafe direction.

## Backup/restore/disaster recovery, RPO/RTO

**This is the most consequential item in this checklist — read in full,
do not skim.**

Source: `fornax-cloud`'s `docs/fornx-214-dr-drill.md` (the drill) and
`docs/fornx-439-production-dr-investigation.md` (the follow-up that
re-confirmed the limitation live and investigated workarounds).

- **Measured**: RPO ~76 seconds, RTO ~27 seconds, both well inside <5
  minute targets — but measured against a **real seeded failure on the
  Neon project's root branch**, with verified FK consistency and safe
  double-replay idempotency.
- **Not measured, and not currently possible**: a `production`/`beta`
  restore. Neon's snapshot/restore mechanism only operates on a project's
  root branch; `production` and `beta` are non-root child branches.
  FORNX-439 re-confirmed this live (2026-10-09) and checked for a
  workaround (time-travel branch creation) — none exists on the current
  Neon API surface. Restoring the root branch only recovers the shared
  fork-point ancestry, not `production`/`beta`'s own post-fork history (3+
  weeks of real data as of FORNX-439's investigation).
- **The only identified real mitigation — a scheduled `pg_dump` outside
  Neon's branch mechanism — has not been built.** This is a genuine,
  disclosed release-boundary gap, not a resolved item with a comforting
  number attached to it.
- A related hardening gap noticed in passing, not yet acted on:
  `production`'s Neon branch has `protected: false` (Neon's free-tier plan
  allows 0 protected branches) — flagged as a candidate for a future
  hardening ticket, not fixed here.

**Declared v0.0.9 DR posture**: database-layer backup/restore mechanics are
proven to work (on disposable/root-branch data); `production`/`beta`
specifically have no working point-in-time restore today. Any release
communication must say this plainly, not imply DR is solved because a
drill produced good numbers on the wrong branch.

## Storage/cost architecture decision

Source: `fornax-cloud`'s `docs/fornx-213-storage-benchmark.md`. Decision:
stay on Postgres/Neon. Real measured growth ~2.1 KB/session-bundle, linear
through 100,000 synthetic sessions; query latency flat and index-backed
through the same range. No migration plan needed — nothing measured
justifies ClickHouse/BigQuery/Kafka. Revisit when a single branch
approaches ~500MB (half the configured 1 GiB Neon branch-size cap) or a
real production query is observed exceeding ~1s.
