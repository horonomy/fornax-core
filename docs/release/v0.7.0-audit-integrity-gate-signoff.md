# v0.7.0 Audit Integrity Gate sign-off

Jira: FORNX-323 (`fornax-core` half) · Epic: FORNX-70 (Release Gate).

This document is the FORNX-323 Release Gate evidence for the audit subsystem
built by FORNX-315 (local hash-chained ledger), FORNX-317 (signed remote
checkpoints), and FORNX-319 (retention/purge). It adds no product surface —
every claim below is proven by a test that attacks the already-built code
through its own public API plus, where noted, a second raw SQLite connection
standing in for an attacker with direct filesystem access. It does not
re-prove what FORNX-315/317's own test suites already cover (payload edit,
middle-row delete, tail truncation, prev_hash relink; the checkpoint payload's
flat-vs-nested and domain-confusion regressions) — see those modules' own
test lists for that coverage.

### Gate items, mapped to the exact test that proves each

| Gate item | Test | What it proves |
|---|---|---|
| A direct-SQL attempt to reuse an existing `seq` value is refused | `direct_sql_seq_reuse_insert_is_rejected_by_the_primary_key_constraint` | `audit_events.seq` is `INTEGER PRIMARY KEY` (SQLite rowid alias) — a literal second row at an occupied `seq` is rejected by the database engine itself, a stronger guarantee than post-hoc detection. |
| An out-of-order insert that skips the high-water allocation mechanism is caught | `direct_sql_out_of_order_insert_skipping_high_water_is_detected_as_missing_seq` | Inserting `seq=15` directly when only `1..=10` exist (bypassing `append_audit_event_locked` entirely) is caught as `DivergenceKind::MissingSeq` at `seq=11` by the same linear-scan check that already catches deleted middle rows — no new detection code needed; the existing `expected_seq` invariant already generalizes to this case. |
| Whole-file replacement is provably undetectable by the local chain alone | `whole_file_replacement_is_invisible_to_the_local_chain_alone_but_caught_by_a_prior_checkpoint` (Part A) | An attacker who replaces the entire `fornax.db` with a different, internally self-consistent chain (own genesis, own valid sequence) produces a chain that `verify_audit_chain` reports `Valid`. This is asserted explicitly as a **limitation**, matching `audit_ledger.rs`'s own trust-boundary doc comment ("only binds this store's own rows to each other, not to any ground truth outside the store") — not silently relied upon. |
| Whole-file replacement IS caught when a prior checkpoint receipt exists | `whole_file_replacement_is_invisible_to_the_local_chain_alone_but_caught_by_a_prior_checkpoint` (Part B) | The same replacement, compared against a real, independently-verified `SignedAuditCheckpoint` from the original chain (never persisted in the replaced file, standing in for the cloud-recoverable copy ADR-0012 §7.4/§8.1 describes) via `evaluate_checkpoint_consistency`, is caught: `AnchorMissing` when the replacement is shorter than the attested head, `AnchorRewritten` when a row occupies the attested `seq` with different content. Both branches of ADR-0012 §8.2 rows 3–4 are exercised end to end. |
| Rollback-then-diverge against a receipted checkpoint is the strongest verdict | `rollback_then_diverge_against_a_receipted_checkpoint_is_attested_prefix_corrupted` | The exact ADR-0012 §8.2 worked example, end to end with real stores: a direct-SQL attacker rewinds past a checkpointed head (`DELETE FROM audit_events WHERE seq > 5`, leaving the untouched, monotonic `audit_ledger_high_water` marker at `10`); the legitimate process, unaware, appends through `Store`'s own API and lands at `seq=11` with a `prev_hash` naming an erased row. `verify_audit_chain` reports `MissingSeq` at `seq=6`; `evaluate_all_checkpoint_receipts` classifies this as `AttestedPrefixCorrupted { first_bad_ledger_seq: 6, .. }` because the divergence sits at-or-before the attested `head_ledger_seq=10` — the strongest of the five §8.2 verdicts, proving the corruption is recognized as lying *inside* the range the cloud already witnessed. |
| No code path, log line, doc comment, CLI string, or doc file overclaims what verification proves | `no_source_or_doc_overclaims_what_audit_verification_proves` | Source-inspection test (mirroring `audit_ledger.rs`'s own `no_write_path_other_than_append_audit_event_touches_audit_events` precedent). Part A confirms the required caveat language ("does NOT attest that the endpoint recorded every event", "does NOT make a compromised endpoint trustworthy", the ADR-0012 "witness statement... Nothing more" framing) is present in `audit_ledger.rs`, `audit_checkpoint.rs`, ADR-0011, and ADR-0012. Part B scans every tracked `.rs`/`.md` file in the repository for uncaveated absolutist phrases (`tamper-proof`, `guarantees completeness`, `trustworthy endpoint`, `complete audit trail`, `cannot be tampered with`, etc.) and fails if any exist outside this test file itself. At the time of this pass, zero such phrases exist anywhere else in the repository — this is a genuine regression guard, not theater; it will fail the moment a future PR adds one. |

### What this suite does NOT detect, stated explicitly

The gate's honesty matters more than its coverage count. In addition to the
limitations `audit_ledger.rs`'s and `audit_checkpoint.rs`'s own module docs
and ADR-0011/ADR-0012 already state (an endpoint that never calls
`append_audit_event` produces a `Valid` chain while silently incomplete; a
fully-compromised Fornax process can fabricate a self-consistent chain from
scratch, including events that never happened, and can even get it
checkpointed), this suite specifically does not detect:

1. **Whole-file replacement with no checkpoint anchoring at all.** If the
   device has never submitted (or the verifier has no access to) any prior
   checkpoint receipt for the device, a wholesale file swap is genuinely
   undetectable — there is no external reference point to compare against.
   `whole_file_replacement_is_invisible_to_the_local_chain_alone_but_caught_by_a_prior_checkpoint`
   proves this directly (Part A) rather than merely asserting it in prose.
2. **An attacker who controls checkpoint submission and simply never
   submits one.** Checkpoint anchoring only closes the gap for periods a
   checkpoint was actually issued and verified for. A device (or an
   attacker with full control of the local daemon process) that disables or
   suppresses checkpoint submission entirely reduces to case 1 for its
   entire unanchored history — no test in this repository can prove
   detection of an event that structurally cannot occur, and this document
   does not claim one does.
3. **An attacker with full process control who forges a checkpoint-anchored
   row correctly.** If the attacker can both rewrite `audit_events` rows
   *and* recompute hashes forward *and* has already obtained (or forged) a
   matching signed checkpoint for the forged content, no local or
   checkpoint-anchored check in this codebase can distinguish it from
   genuine history — this is the same "compromised endpoint" limit ADR-0011
   §(trust boundary) and ADR-0012 §1 already state; forging a *valid
   signature* over fabricated content additionally requires possession of a
   trusted signing key, which is outside `fornax-core`'s device-side trust
   boundary entirely (key custody is a `fornax-cloud`/issuer-side property).
4. **Between-checkpoint tampering that is repaired before the next
   checkpoint is issued.** `evaluate_checkpoint_consistency` compares the
   CURRENT chain state against previously stored receipts at evaluation
   time. A rollback-then-replay attack that fully restores the exact
   original bytes before the next checkpoint submission and before any
   verification pass runs leaves no trace for this mechanism to find (it
   would, however, still need to reproduce the exact original hash chain
   bit-for-bit, which requires knowing every original payload — a much
   narrower attack surface than free-form tampering).
5. **Seq reuse via `INSERT OR REPLACE` (as opposed to a second `INSERT`).**
   The primary-key-rejection test above proves a literal duplicate row is
   impossible. It does not — and cannot — prevent `INSERT OR REPLACE`
   (or an `UPDATE`) overwriting the single row at an existing `seq` with
   different content; that is semantically the same attack the existing
   FORNX-315 `direct_sql_payload_mutation_is_detected_as_hash_mismatch`
   test already covers (any content change at a fixed `seq` recomputes to a
   different `entry_hash`), so it is not re-tested here.
6. **Retention/purge interactions with the audit ledger.** FORNX-319's
   `sweep_expired_records`/`purge_evidence_payload` operate on evidence
   records, not `audit_events` — this ticket's scope is the ledger and
   checkpoint mechanisms specifically (per the ticket's own reading list),
   and no test here exercises retention/purge against the audit chain.
