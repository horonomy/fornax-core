# Fornax v0.0.2 — Real Beta Product — Release Notes

**Status:** engineering substantially complete, release candidate. See
`release/v0.0.2-candidate-manifest.json` for the frozen 5-repo SHA pin.
QA/Security sign-off (FORNX-241) has **not** run yet — see "What's not yet
verified" below. FORNX-64 (Stage 2 epic) and FORNX-242/243 (Release,
Post-Release) remain To Do. This document describes the shipped code, not
a completed release; it will be updated once FORNX-241/242/243 complete.

## What this is

Fornax v0.0.2 turns the locally-proven v0.0.1 vertical slice into the
backend and API surface for a real Internet-facing Beta product, without
weakening the local-first trust boundary: raw evidence stays local by
default, upload is policy-controlled and redacted before it ever leaves
the machine, and the local hot path never requires cloud access.

This release is about **fornax-cloud** (the companion cloud-side repo) far
more than fornax-core. fornax-core has no v0.0.2-specific scope — the
v0.0.2 candidate pins it at the same commit as v0.0.1.

## What's included (fornax-cloud)

- **Device onboarding** (FORNX-150/151): self-service device
  register/rotate/revoke over HTTP, least-privilege ingest credentials, a
  device list with self-reported and empirically-observed capability
  metadata. See fornax-cloud's `README.md` "Beta device onboarding" section
  for the exact API contract.
- **Authenticated ingest hardening** (FORNX-75/282): the ingest gateway
  requires a valid device credential; uploader token failures fail fast
  instead of silently quarantining every item (FORNX-283).
- **Beta observability** (FORNX-77/153): structured logging reaching
  stdout correctly, alerting groundwork for Cloud Run/Pub/Sub/DB.
  Diagnosable-from-telemetry failure modes, no raw payloads in operational
  logs.
- **Privacy fixtures and migration coverage** (FORNX-79/78): local privacy
  fixtures for redaction testing; migration tests covering both fresh and
  previous-schema Alembic states.
- **Evidence Explorer + decision UX (SaaS)** (FORNX-301/303/305):
  capability-driven frontend/backend split, evidence explorer, decision UX
  for the hosted dashboard.
- **Reliability fixes**: pub/sub device-check hardening, sensitive-path
  redaction (FORNX-284/286), accepted-counter no-op conflict fix
  (FORNX-58), LRU cache settings leak fix (FORNX-294), backend startup
  without Application Default Credentials (FORNX-300).
- **Provider-neutral billing foundation** (FORNX-46, landed under
  fornax-cloud's own v0.0.3 branch prefix per its actual PR history —
  see `release/v0.0.2-candidate-manifest.json`'s notes and
  `docs/adr/0003-billing-entitlement-and-provider-boundary.md`): sandbox-only
  Dodo checkout/webhook/entitlement, not part of v0.0.2's shipped scope.

## What this is not

- **Not a live, publicly reachable Beta deployment.** No Fornax Cloud Run
  service, Neon Beta branch, or public ingest endpoint exists today (see
  `gcloud projects list` / `gcloud run services list` against the
  Horonomy account — no Fornax-named project). Everything above is real,
  merged, tested code; none of it has been deployed to a live environment
  yet. FORNX-64's own release gate ("a real BETA READY gate using actual
  Claude Code and Codex traffic") is explicitly not satisfied by
  implementation tickets alone, and that gate has not run.
- **Not self-service today.** Device registration is unauthenticated by
  design (create-only, 409-on-collision) once a Beta backend is reachable,
  but the backend itself is not exposed for public registration — it
  stays access-controlled until the Beta trust-model cutover (FORNX-137).
  `fornax-docs`' Quick Start and `fornax-website`'s Pricing/Security pages
  correctly mark this "Beta — coming soon" pending that ticket, not
  FORNX-151 (which is Done) — that stale cross-reference was found and
  fixed as part of this release's docs pass.
- **No user/tenant/account system.** Confirmed by FORNX-151's implementer:
  there is no account model anywhere in this schema. "Sign in to a Beta
  account" (from FORNX-64's non-goals-adjacent language) has no backing
  model; device identity is the only identity primitive that ships in
  v0.0.2.

## What's not yet verified

FORNX-241 (QA/Security assurance) has not run. What *has* been verified
mechanically as part of this release-notes pass, against a real throwaway
Postgres instance (no mocks):

- fornax-cloud backend: `ruff format --check`, `ruff check`, `mypy` — all
  clean. `pytest -v`: **597 passed, 9 skipped, 0 failed** — covering tenant
  isolation (`test_auth_path_isolation.py`), OIDC replay/state resistance
  (`test_oidc_state_and_replay.py`), CSRF protection, credential-never-logged
  negative paths, rate limiting, Alembic migrations (fresh + previous
  schema), write-time redaction, and billing idempotency/reconciliation.
  The 9 skips are self-documented pre-existing gaps needing a local Pub/Sub
  emulator (8) or a local Keycloak instance (1) — not run this pass, not
  rounded up to a pass.
- fornax-cloud Rust workspace (`fornax-ingest`, `fornax-uploader`):
  `cargo clippy --workspace --all-targets -- -D warnings` clean; `cargo
  test --workspace`: **91 passed, 0 failed**.
- fornax-cloud frontend: `typecheck`, `lint`, `test` all pass (**86/86**
  tests).
- fornax-docs: `npm run build` (Docusaurus, broken-link checking on)
  passes clean.
- fornax-website: `typecheck`, `lint`, `build` all pass.

What this does **not** cover: anything requiring a live network path —
real Internet retries/timeouts/offline recovery, real device-to-Beta
enrollment, real Cloud Run/Pub/Sub under production conditions, browser
E2E against a deployed SaaS UI, or the actual fresh-install user journey
FORNX-241/FORNX-64 require. Those need a deployed Beta environment, which
does not exist yet — disclosed here rather than assumed passing.

## Migration notes

fornax-core scope). `fornax-cloud`'s Alembic migrations are additive and
covered by `test_migrations.py`'s fresh-and-previous-schema tests.
