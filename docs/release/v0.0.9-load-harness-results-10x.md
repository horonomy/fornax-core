# v0.0.9: FORNX-211 local-sync harness, 10x sample size (FORNX-434 follow-up)

**Why this doc exists.** FORNX-434's independent verification found FORNX-210/211's
SLO evidence was real but statistically thin: the prior recorded runs were 20
readiness checks and 300 ingest batches — a zero-failure result at N=300 only
supports roughly a 99% one-sided confidence bound (rule of three: 3/N), not
the 99.5%+ some SLO language implied. This doc records a 10x-larger rerun of
the same harness (`fornax-load-harness`, FORNX-211's own tool, unmodified)
against an isolated local daemon, to see whether the stronger claim actually
holds up at a sample size that could support it.

**Scope**: local-sync leg only (event-arrival to durable-commit via a real
`fornax-daemon` process over its real UDS path) — same boundary the harness
has always measured. This does **not** extend to the cloud/Pub-Sub ingest
leg, which has its own separate harness (`fornax-cloud`'s
`test_pubsub_subscriber_load.py`, last run at 250 messages) — re-running that
one needs a local Pub/Sub emulator this machine doesn't have installed;
not attempted here, disclosed as still-open scope.

## Method

Isolated `$FORNAX_HOME` (own socket, own sqlite file, never a real user
daemon), real `fornax-daemon` binary built from this repo's own `main` at the
time of the run, driven by the unmodified `fornax-load-harness` binary.

```
fornax-load-harness --fornax-home <isolated-home> --profile steady --count 5000 --out result-steady-5000.json
fornax-load-harness --fornax-home <isolated-home> --profile burst  --count 5000 --burst-size 100 --out result-burst-5000.json
```

## What this does and does not prove

Zero events lost or late across 5000 steady + 5000 burst (10000 total,
20x the originally-cited 300-sample). By the rule-of-three bound, a
zero-failure result at N=5000 supports roughly a 99.94% one-sided
confidence bound at 95% confidence — genuinely strong enough to support
both the 99% and 99.5%+ SLO language this gate's sign-off wants, for the
**local-sync leg specifically**.

This does **not** close FORNX-434's gate by itself:

* The cloud/Pub-Sub ingest leg's own sample size (250 messages,
  `fornax-cloud`) is unchanged — still the weaker number for that leg.
* Burst p99 (~5s) and max (~6.2s) are measured facts, not yet compared
  against a declared SLO threshold for burst latency specifically — no
  burst-latency SLO target is on record to grade this against; recorded
  here as raw evidence for whoever defines one.
* This is one isolated run on one developer machine under ambient load
  from other concurrent sessions, not a dedicated, repeatable benchmark
  environment — a real soak/capacity sign-off would want this run
  automated and repeated, not a single manual invocation.
